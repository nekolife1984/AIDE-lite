# 課題ファイル形式

各課題を`.work/tasks/T-0001-short-title.md`のようなMarkdownファイルで管理する。先頭のYAML front matterを機械可読な項目、本文を人が読む目的・完了条件・進捗の記録に使う。

## front matter

| 項目 | 必須 | 説明 |
|---|---:|---|
| `id` | はい | 一意で不変な課題ID（`T-0001`） |
| `title` | はい | 課題の短い名前 |
| `status` | はい | `backlog`、`ready`、`in_progress`、`blocked`、`in_review`、`done`、`cancelled`のいずれか |
| `priority` | はい | `low`、`medium`、`high` |
| `project` | はい | 所属するプロジェクトID。なければ`null` |
| `depends_on` | はい | 先に完了が必要な課題IDの配列。なければ`[]` |
| `created` | はい | 作成日（`YYYY-MM-DD`） |
| `updated` | はい | 最終更新日（`YYYY-MM-DD`） |

日付はISO 8601形式にする。状態を変えたら`updated`も更新する。状態一覧にない独自値を追加せず、必要なら運用ルールを先に変更する。

## 本文

本文には、少なくとも次を記載する。

- **目的**：背景と解決したいこと
- **完了条件**：確認可能なチェック項目
- **進捗**：作業の節目、実施した検証と結果
- **ブロッカー・次の作業**：該当する場合に解除条件と再開手順

作業コマンドごとの逐次ログは避け、再開やレビューに役立つ節目をまとめる。状態はfront matterを正本とし、本文に別の「現在の状態」を重複して書かない。

## 状態の意味

| 状態 | 意味 |
|---|---|
| `backlog` | 未整理、または着手順が未確定 |
| `ready` | 目的と完了条件が明確で、依存も解決し着手可能 |
| `in_progress` | 実作業中 |
| `blocked` | 外部要因や未完了の依存により進められない |
| `in_review` | 作業が終わり、レビューや確認を待っている |
| `done` | 全完了条件を検証し、必要な変更が取り込まれた |
| `cancelled` | 実施しないと決定。本文に理由を残す |

依存が解消し、着手可能になったら`ready`へ移す。ブロッカーを解除したら、実際の状況に応じて`ready`または`in_progress`へ戻す。

## プロジェクトファイル

複数課題に共通する目的・スコープ・ロードマップをまとめる場合だけ`.work/projects/P-0001-short-name.md`を作る。課題IDの一覧を参照情報として記載し、詳細な完了条件や進捗は各課題ファイルに保つ。プロジェクトのひな形は[.agents/templates/project.md](../templates/project.md)を使う。
