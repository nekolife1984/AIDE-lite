# 設計原則

## 課題ファイルを正本にする

`.work/tasks/`に、課題1件につきMarkdownファイル1つを置く。状態別フォルダには分けず、状態はfront matterの`status`だけに記録する。ファイル移動や状態の二重更新を避け、課題IDと参照先を安定させる。

## 構成

```text
.work/
├── tasks/                  # 課題ファイルをフラットに配置
│   ├── T-0001-example.md
│   └── T-0002-another.md
└── projects/               # 任意の目的・ロードマップ
    └── P-0001-example.md

.agents/templates/
├── task.md
└── project.md
```

完了・中止後も課題ファイルを同じ場所に残す。最初からアーカイブ移動や生成ボードを必須にせず、検索・一覧生成が必要になった時点で追加する。

## 安定した識別子

- 課題IDは`T-0001`形式、プロジェクトIDは`P-0001`形式とし、重複・再利用をしない。
- 新規IDは既存の最大番号に1を足して採番する。
- 参照にはIDを使い、可変のファイル名やパスに依存しない。
- ファイル名はIDと短い説明を含める（例：`T-0001-config-loading.md`）。

## Gitを履歴と共有に使う

本文・状態・進捗の変更はGit差分で追える。複数人で編集する場合は、通常のブランチ／Pull Request運用を使い、同じ課題ファイルの同時編集を避ける。Git履歴は変更の記録であり、課題本文に必要な現在の状態や再開情報を省略する理由にはしない。
