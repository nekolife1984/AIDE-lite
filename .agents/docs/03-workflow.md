# 起票から完了まで

## 1. 重複・依存を確認する

`.work/tasks/`内の既存タイトル・目的・関連IDを検索する。同じ目的の課題があれば新設せず既存ファイルを更新する。別の成果物なら独立した課題にし、関連IDを記録する。先行作業が必要な場合は`depends_on`に課題IDを指定する。

## 2. 課題の分割基準

- 独立した成果があり、それぞれに確認可能な完了条件を設定できる場合は分ける。
- 単なる内部手順や、単独では完了を確認できない作業はまとめる。
- 技術レイヤーやファイル単位ではなく、利用者から確認できる機能・成果を基本に分ける。
- 各課題に必要なテストを含める。複数機能を横断するテストは、それ自体が独立した成果となる場合に限り別課題にする。

## 3. 課題を作成する

1. 既存IDの最大番号を確認し、未使用の次のIDを採番する。
2. `.agents/templates/task.md`を`.work/tasks/T-XXXX-short-title.md`へコピーする。
3. 目的、優先度、完了条件、依存関係を記入する。
4. すぐ着手可能なら`ready`、それ以外は`backlog`にする。

## 4. 着手・進捗を記録する

作業開始時に`status`を`in_progress`へ変更し、`updated`を更新する。設計決定、作業のまとまり、検証、ブロッカーの発生・解消など、再開やレビューに役立つ節目で本文の進捗欄を更新する。

進捗記録には次を含める。

- 完了した作業と変更ファイル
- 実行した検証と実際の結果
- 未解決点・ブロッカー
- 次に行う具体的な作業

## 5. ブロック・中断・再開

進行を妨げる具体的な要因がある場合は`blocked`にし、理由・解除条件・次の作業を記録する。単に一時中断するだけならブロッカー扱いにせず、`in_progress`のまま再開情報を残す。再開時は課題ファイルと作業ツリーを確認し、記録を現在の状態に合わせて更新する。

## 6. レビュー・完了

作業が完了条件を満たしたら`in_review`にして確認を依頼する。指摘に対応するときは`in_progress`へ戻す。全完了条件を検証し、必要な変更が取り込まれた後に`done`へ変更する。未達条件があるまま完了扱いにしない。

実施しないと決めた課題は削除せず`cancelled`にし、理由を残す。完了・中止した課題を移動・削除しないことで、ID参照と履歴を保つ。
